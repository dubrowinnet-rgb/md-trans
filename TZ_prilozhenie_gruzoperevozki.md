# ТЗ (черновик v4): SaaS-приложение для управления заказами грузоперевозок

> Составлено на основе анализа референса — приложения Bumpix (CRM для бьюти-мастеров) и его
> веб-кабинета. Продукт задуман как **мультитенантный SaaS**: сервис для перевозчиков с
> подпиской за каждого сотрудника (водителя/грузчика).
> Раздел 10 — последние открытые вопросы перед передачей в Claude Code.

---

## 1. Бизнес-контекст

- **Сфера:** грузоперевозки — Газель по городу/межгород, услуги грузчиков, утилизация мебели,
  демонтаж, вывоз мусора, сборка мебели.
- **Модель продукта:** SaaS. Каждая компания-перевозчик — отдельный тенант с изолированными
  данными. Монетизация — подписка за каждого сотрудника отдельно (раздел 8).
- **Ключевой сценарий:** перевозчик (он же чаще всего диспетчер) принимает звонки клиентов,
  заводит заказ в приложении, описывает всё необходимое и назначает исполнителей —
  конкретных водителя и грузчиков. Исполнители получают push-уведомление и подтверждают
  получение заказа (раздел 9.5) — это заменяет по надёжности звонок/смс себе на замену.
- **Расчёт стоимости заказа** в MVP — **ручной, диспетчер вписывает сумму сам**. Автоматический
  расчёт по формуле (переработка, доплаты) — это пункт для версий **после MVP**, подробности
  зафиксированы в разделе 9.3, но не реализуются на первом этапе.

## 2. Роли

| Роль | Уровень | Что делает |
|---|---|---|
| Супер-админ (вы, владелец SaaS) | Платформа целиком | Видит все тенанты, управляет тарифами, следит за оплатами |
| Владелец / диспетчер компании-тенанта | Один тенант | Регистрируется самостоятельно, ведёт заказы, добавляет и оплачивает сотрудников, ведёт клиентов и скидки |
| Водитель | Сотрудник тенанта | Свой мобильный экран: заказы на день, точки маршрута, груз, состав назначенных грузчиков, подтверждение получения заказа, статус выполнения, звонок клиенту |
| Грузчик | Сотрудник тенанта | Свой мобильный экран, аналогичный экрану водителя. У одного грузчика в день может быть несколько заказов с разными водителями или без водителя вообще |
| Клиент компании-тенанта | Не пользователь приложения | Заявки принимает диспетчер вручную по звонку |

Водитель и грузчик — две роли одной сущности `Employees`: общая логика подписки, блокировки
аккаунта и подтверждения заказов, разные (но структурно похожие) мобильные экраны.

## 3. Что переносим из референса без изменений

- Календарь по исполнителям-колонкам (день/неделя/месяц), с цветовой кодировкой
- Быстрое создание заказа через модалку
- Каталог услуг: название, длительность по умолчанию, базовая цена, мультивыбор
- Push-напоминания за N минут до события
- Учёт доходов/расходов, отчёты и планирование
- Лист ожидания
- Полноценный веб-кабинет для диспетчера (раздел 5.1)

## 4. Что меняем принципиально (ядро доработки)

1. **Точки маршрута.** Обычно 1 точка загрузки + 1 точка выгрузки, но можно добавить
   дополнительные точки. **Важно для экрана водителя:** основные 2 точки показываются
   заметно и просто, дополнительные — сворачиваются/показываются по клику «ещё точки»,
   чтобы не перегружать основной экран информацией.
2. **Разделение «Клиент» и «Точка маршрута».** Клиент — реальные данные заказчика, включая
   персональную скидку в процентах, которая **применяется автоматически ко всем его заказам**.
3. **Справочник «Транспорт»** отдельно от водителя.
4. **Поле «Детали груза».**
5. **Ручной ввод стоимости заказа в MVP.** Автоматический расчёт (переработка/доплаты) —
   после MVP, детали формулы зафиксированы заранее в разделе 9.3, чтобы не потерять их к тому
   моменту.
6. **Статус-машина заказа**, включая статус подтверждения получения заказа сотрудниками
   (раздел 9.5) — это отдельный, более важный на старте механизм надёжности, чем сама
   стоимость заказа.
7. **Роль «Грузчик»** и явное назначение конкретных людей на заказ через `OrderCrew`.
8. **Проверка занятости сотрудника по времени.** При назначении водителя или грузчика на
   заказ система не должна давать выбрать сотрудника, если по времени он уже занят на другом
   заказе (пересечение интервалов `scheduled_start`–`scheduled_end`). Это ключевая функция
   для удобства диспетчера — избежать случайного назначения одного грузчика на два заказа
   одновременно.
9. **Мультитенантность и подписка по сотрудникам** — раздел 8.

## 5. Структура экранов (первая версия)

| Экран | Назначение | Ключевые отличия от референса |
|---|---|---|
| Календарь по водителям | Главный экран диспетчера | Карточки показывают адрес, статус подтверждения и состав экипажа |
| Создание заказа | Модалка → форма | Точки маршрута, назначение водителя и грузчиков с проверкой занятости по времени |
| Карточка заказа | Просмотр/редактирование | Точки маршрута (осн. + доп.), транспорт, статус, груз, экипаж, статус подтверждения каждым сотрудником, сумма (вручную) |
| База клиентов | Список + поиск | Клиент = реальный заказчик, персональная скидка |
| Каталог услуг | Управление прайсом | Как в референсе |
| Сотрудники | Список водителей/грузчиков, статус оплаты, добавление, переименование аккаунта при замене сотрудника | Новый раздел |
| Экран водителя (моб.) | Заказы на день, основные точки маршрута крупно + доп. точки по клику, состав грузчиков, кнопка подтверждения получения заказа, звонок, навигация | Новый экран |
| Экран грузчика (моб.) | Аналогично экрану водителя, независимо от того, есть ли водитель на заказе | Новый экран |
| Архив заказов | Фильтры по датам/статусам/сотрудникам, экспорт в Excel | Новый экран (раздел 9.6) |
| Отчёты | Доходы/расходы, по сотрудникам, по услугам | Плюс фильтр по статусам |
| Веб-кабинет диспетчера | Календарь, заказы, сотрудники, биллинг — desktop-версия | Раздел 5.1 |

### 5.1. Веб-кабинет диспетчера

Полноценная веб-версия календаря (как на скрине Bumpix), а не урезанная копия. Совмещает
операционную работу (календарь, заказы, клиенты) и административную (сотрудники, оплата
подписки, экспорт архива в Excel) в одной панели — удобно диспетчеру работать с компьютера.

## 6. Черновая модель данных

```
Organizations (id, name, created_at)

Employees    (id, org_id, role [driver/loader], name, phone,
              account_status [active/pending_payment/suspended],
              paid_until, monthly_price)
              -- last_location [lat, lng, updated_at] — служебное поле для будущего
              -- GPS-трекинга, не используется в MVP, ни в одном экране не отображается.
              -- Заведено заранее, чтобы позже не переделывать структуру таблицы.

Vehicles     (id, org_id, driver_employee_id, plate, model, capacity)
Clients      (id, org_id, name, phone, discount_percent, notes)
Services     (id, org_id, name, base_duration, base_price, category)

Orders       (id, org_id, client_id, status,
              cargo_description,
              scheduled_start, scheduled_end,
              actual_price,            -- вводится диспетчером вручную в MVP
              comment, photos[])
OrderStops   (id, order_id, type [pickup/dropoff], address, order_index, is_primary)
OrderCrew    (order_id, employee_id, role [driver/loader],
              status [notified/read/confirmed], notified_at, read_at)
OrderServices (order_id, service_id, qty)
Reminders    (id, order_id, remind_at)
Transactions (id, org_id, order_id?, type[income/expense], amount, date)

EmployeeBilling (id, employee_id, period_months [3/6/12], amount, discount_percent,
                  period_start, period_end, status, payment_method [card/sbp])
```

**Пояснения к новым/изменённым полям:**

- `OrderCrew.status` + `notified_at`/`read_at` — механизм подтверждения получения заказа
  (раздел 9.5): диспетчер видит, кто из назначенных сотрудников открыл и увидел заказ.
- `OrderStops.is_primary` — помечает основную точку загрузки/выгрузки, чтобы экран водителя
  показывал их крупно, а остальные — свёрнутыми.
- Поля `base_price`/`hourly_overage_rate`/`price_is_manual` из предыдущей версии документа
  **убраны из MVP** — в `Orders` остаётся только `actual_price`, заполняемый диспетчером.
  Формула для автоматического расчёта откладывается на после MVP (см. раздел 9.3).
- `EmployeeBilling.discount_percent` — 0% на 3 мес, 10% на 6 мес, 20% на 12 мес.

**Важная бизнес-логика (не поле, а правило):** при назначении сотрудника на заказ через
`OrderCrew` система должна проверять, что у этого `employee_id` нет другого заказа с
пересекающимся интервалом `scheduled_start`–`scheduled_end`, и не давать назначить, если
пересечение есть.

## 7. Технологический стек

- **Мобильное приложение:** React Native + Expo (iOS + Android)
- **Backend:** Supabase (Postgres + Auth + Storage + realtime), мультитенантность через RLS
- **Карты/навигация:** только Яндекс.Карты API (геокодинг/автокомплит) и Яндекс.Навигатор
  (deep link для построения маршрута из карточки заказа)
- **Push:** Expo Notifications — используются и для напоминаний, и для механизма подтверждения
  получения заказа (раздел 9.5)
- **Сборка и публикация:** EAS Build
- **Веб-кабинет диспетчера + биллинг:** отдельное веб-приложение (например, Next.js) поверх
  того же Supabase-бэкенда, с рекуррентными платежами **только банковской картой/СБП**
  (счёт на р/с не предусмотрен)
- **Экспорт данных:** генерация Excel-файлов (архив заказов, база клиентов со всеми полями
  карточек заказа) — на бэкенде или в веб-кабинете

## 8. Мультитенантность и подписка по сотрудникам — зафиксированная модель

| Параметр | Значение |
|---|---|
| Кто платит | Перевозчик (владелец/диспетчер тенанта) |
| За что платит | За каждого сотрудника отдельно |
| Цена | Водитель — 300 ₽/мес, грузчик — 200 ₽/мес |
| Минимальный период | 3 месяца по полной цене |
| Скидка за 6 месяцев | 10% |
| Скидка за 12 месяцев | 20% |
| Добавление сотрудника | Аккаунт создаётся только после предоплаты за него |
| Регистрация тенанта | Полностью самостоятельная |
| При увольнении сотрудника | Возврат остатка **не предусмотрен**. Владелец может переименовать существующий (уже оплаченный) аккаунт на нового сотрудника вместо создания нового |
| Предупреждения | За 7 дней и за 3 дня до истечения оплаты — уведомление диспетчеру |
| При истечении оплаты | Приложение сотрудника не получает новые заказы, показывается экран «Работа аккаунта приостановлена, пополните счёт» |
| Способ оплаты | Только банковская карта / СБП, рекуррентный платёж. Оплата по счёту на р/с — не предусмотрена |

## 9. Решённые открытые вопросы (детали для разработки)

### 9.1. Точки маршрута и назначение экипажа
Основные 2 точки + возможность добавить дополнительные (раздел 4, п.1). Диспетчер явно
назначает водителя и грузчиков, система проверяет их занятость по времени (раздел 4, п.8).

### 9.2. Скидка клиента
Задаётся в процентах в карточке клиента, применяется автоматически ко всем его заказам —
но так как стоимость в MVP вводится вручную, это скорее справочная информация для диспетчера
при вводе суммы, а не автоматический вычет (автоматизация — после MVP, см. 9.3).

### 9.3. Формула цены — отложено на после MVP, но зафиксировано заранее
Чтобы не потерять контекст к моменту, когда до этого дойдут руки:
- Переработка сверх включённого времени: 1–15 минут — округление **вниз** (не считается),
  с 16-й минуты — округление **вверх** до полного часа.
- Доплата за расстояние отдельным полем — **не нужна**, разница «по городу/межгород» уже
  полностью заложена в разные позиции каталога услуг.
- Скидка клиента применяется после расчёта почасовой доплаты.

### 9.4. Трекинг сотрудника
Не реализуется в MVP. Поле `last_location` зарезервировано в `Employees`, не используется
ни в одном экране (см. пояснение в разделе 6).

### 9.5. Подтверждение получения заказа сотрудниками
Когда диспетчер назначает на заказ водителя и/или грузчиков, каждому из них приходит push
«Получен новый заказ». Как только сотрудник открывает заказ в своём приложении, статус в
`OrderCrew` меняется на `read`/`confirmed`, и диспетчер в карточке заказа видит отметку
«заказ увиден и принят» по каждому участнику — это подтверждение, что связь не подвела и
человек в курсе, без необходимости звонить и спрашивать лично.

### 9.6. Архив заказов и выгрузка данных
Нужен архив заказов с фильтрами (по датам, статусам, сотрудникам) и экспортом в Excel, а
также отдельная выгрузка базы клиентов в Excel со всеми полями из карточек их заказов.

### 9.7. Кастомизация тенантов
На данном этапе не нужна — единый интерфейс для всех тенантов.

### 9.8. Оплата заказов грузоперевозок клиентами
Происходит вне приложения (наличные/перевод) — не путать с оплатой подписки за сотрудников.

## 11. Как оформить финальный промпт для Claude Code

1. Бизнес-контекст, модель SaaS и роли — водители и грузчики как «Сотрудники» (разделы 1–2)
2. Экраны, включая мобильные экраны водителя/грузчика и веб-кабинет (раздел 5)
3. Модель данных с мультитенантностью, `OrderCrew` и проверкой занятости по времени (раздел 6)
4. Решения по биллингу за сотрудников (раздел 8)
5. Технологический стек — Яндекс.Карты/Навигатор, веб-кабинет, экспорт в Excel (раздел 7)
6. Явно указать: **в первой версии стоимость заказа вводится диспетчером вручную**,
   автоматический расчёт — не делать вообще на этом этапе (раздел 9.3 — только справочно,
   не для реализации)
7. Порядок разработки — один вертикальный срез на уровне одного тенанта, без биллинга:
   авторизация → создание заказа с назначением водителя и грузчиков (с проверкой занятости) →
   push-уведомление и подтверждение получения заказа → отображение в календаре → изменение
   статуса → и только потом расширять на мультитенантность, веб-кабинет и биллинг

Прикладывайте скриншоты референса (включая веб-кабинет) прямо в диалог с Claude Code —
это ускоряет понимание UX-паттернов, которые нужно сохранить.
