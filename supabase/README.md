# Supabase

## Применить схему

Эта сессия не имеет сетевого доступа к `*.supabase.co`, поэтому миграции нужно
накатить самостоятельно одним из способов:

**Вариант А — SQL Editor в Dashboard (быстрее всего):**
1. Откройте ваш проект → SQL Editor → New query.
2. Скопируйте содержимое `migrations/0001_init_schema.sql` целиком и выполните (Run).
3. Так же выполните `migrations/0002_create_order_function.sql` (нужна для экрана создания заказа)
   и `migrations/0003_push_tokens.sql` (колонка для push-токена сотрудника).
4. Выполните `migrations/0004_services_catalog.sql`: цвета услуг, стартовый
   каталог услуг и новая версия `create_order` (с услугами и обязательным клиентом).
   Без неё новая форма заказа не сохранит заказ.
5. Выполните `migrations/0005_roles_and_permissions.sql`: роли входа
   (администратор/диспетчер/водитель/грузчик), логин и права доступа у
   каждого сотрудника, удаление заказа. **После неё сразу же, до того как
   зайти в приложение заново, выполните шаг «Сделать себя администратором»
   ниже** — иначе ваш текущий вход останется без роли и приложение покажет
   экран «нет доступа».
6. Выполните `migrations/0006_fixed_role_permissions.sql`: узкое право
   водителя редактировать только время и сумму заказа (остальные поля
   заблокированы триггером в базе, а не только в интерфейсе) и колонка
   `orders.created_by` для статистики администратора по сотрудникам.
7. Выполните `migrations/0007_fleet_and_schedule.sql`: автопарк (таблица
   `vehicles`), рабочий график (`employee_days_off`) и разрешение для
   водителя вести два и более заказа одновременно («сборный груз») — без
   неё не заработают вкладки «Автопарк» и «График» и выбор машины в заказе.
8. Выполните `migrations/0008_schedule_modes_hours_and_moves.sql`: режим
   графика на сотрудника (отмечать выходные или рабочие дни — каждый
   выбирает сам), часы у отмеченного дня и переименование
   `employee_days_off` → `employee_schedule_days`. Без неё «Мой график» не
   покажет переключатель режима и часы.
9. Выполните `migrations/0009_employee_profile_fields.sql`: фамилия, дата
   рождения, начало работы в компании и адрес проживания у сотрудника. Без
   неё карточка сотрудника на экране «Команда» не сохранит эти поля.
10. Выполните `migrations/0010_employee_personal_vehicle.sql`: марка и гос
    номер личного транспорта у сотрудника.
11. Выполните `migrations/0011_settings_sms_reminders.sql`: раздел
    «Настройки» — шаблоны смс клиентам, правила пуш-напоминаний
    сотрудникам о заказе и планировщик, который их отправляет (раз в 5
    минут, через pg_cron). Если запрос упадёт с ошибкой про `pg_cron` или
    `pg_net` — эти два расширения на вашем проекте выключены: откройте
    Dashboard → Database → Extensions, включите оба (`pg_cron` и `pg_net`),
    затем выполните файл ещё раз. Без этой миграции не заработает ни один
    из пунктов «Настроек» и пуш-напоминания сотрудникам приходить не
    будут.

**Вариант Б — Supabase CLI (если он у вас установлен локально):**
```bash
supabase link --project-ref mjrbqnsvwohmwvapiikr
supabase db push
```

## ⚠️ Сделать себя администратором (обязательно после миграции 0005)

До миграции 0005 роль определялась неявно: вход без строки в `employees`
считался диспетчером с полным доступом — так работал и ваш текущий вход.
После миграции 0005 это правило убрано (иначе любой новый вход был бы
диспетчером по умолчанию — дыра в безопасности), и вход без строки в
`employees` видит экран «нет доступа». Чтобы не потерять доступ к
собственному приложению, сразу после 0005 выполните в SQL Editor:

1. Authentication → Users → найдите свою запись (по email, которым входите
   в приложение) → скопируйте её `UID`.
2. Выполните, подставив свой UID:
   ```sql
   insert into employees (auth_user_id, name, role, can_manage_orders, can_view_client_stats, can_view_contacts_and_amounts, account_status)
   values ('<ваш UID из шага 1>', 'Максим', 'admin', true, true, true, 'active')
   on conflict (auth_user_id) do update set
     role = 'admin',
     can_manage_orders = true,
     can_view_client_stats = true,
     can_view_contacts_and_amounts = true;
   ```
3. Перезайдите в приложение (или потяните экран, чтобы обновить сессию) —
   должна появиться вкладка «Команда». Дальше диспетчеров, водителей и
   грузчиков можно заводить прямо в приложении, без SQL.

## Деплой Edge Function (нужна для создания и редактирования аккаунтов из приложения)

Экран «Команда» заводит логин и пароль сотруднику через серверную функцию
`create-account`, а меняет их у уже созданного — через `update-account`; с
телефона нельзя напрямую задать или сменить пароль пользователю (для этого
нужен service role key, а он не должен попадать в приложение). Без деплоя
`create-account` кнопка «Добавить» на экране «Команда» будет возвращать
ошибку; без деплоя `update-account` — сохранение изменений в карточке уже
существующего сотрудника (логин, пароль, фамилия, даты, адрес).

Если Supabase CLI не установлен — ставить отдельно не нужно, `npx` сам
скачает его при первом запуске. Флаг `-y` обязателен: без него npx
спрашивает подтверждение на установку («Ok to proceed?»), и если команды
выполняются одна за другой без паузы, этот вопрос «съедает» следующую
строку как ответ, и установка обрывается с `npm error canceled`. Выполните
в терминале, в корневой папке проекта (той, где лежат папки `mobile` и
`supabase`):

```bash
npx -y supabase login                                        # откроется браузер для входа
npx -y supabase link --project-ref mjrbqnsvwohmwvapiikr       # если ещё не делали
npx -y supabase functions deploy create-account
npx -y supabase functions deploy update-account
npx -y supabase functions deploy send-order-sms
npx -y supabase functions deploy send-crew-reminders --no-verify-jwt
```

Больше ничего настраивать не нужно: `SUPABASE_URL`, `SUPABASE_ANON_KEY` и
`SUPABASE_SERVICE_ROLE_KEY` функция получает от платформы автоматически.
`send-crew-reminders` — единственная с флагом `--no-verify-jwt`: её вызывает
не приложение, а планировщик pg_cron (миграция 0011), у которого нет
своего входа в приложение; без этого флага каждый вызов будет получать
ошибку 401, и пуш-напоминания не будут приходить.

## Смс клиентам (миграция 0011)

Текст смс «заказ принят» отправляется автоматически при создании заказа
(функция `send-order-sms`, задеплоенная выше), но реальная отправка
работает только после того, как вы подключите смс-провайдера — без этого
шага функция просто ничего не отправляет (это ожидаемое поведение, не
ошибка: приложение работает как обычно, заказ создаётся, просто смс пока
не уходит).

1. Зарегистрируйтесь на [sms.ru](https://sms.ru/) (или другом провайдере
   — тогда сообщите нам, какой, текущий код рассчитан на sms.ru) и
   получите `api_id` в личном кабинете.
2. Выполните в терминале, в корневой папке проекта:
   ```bash
   npx -y supabase secrets set SMS_RU_API_ID=<ваш api_id>
   ```
3. Повторно деплоить `send-order-sms` после этого не нужно — секрет
   подхватится автоматически при следующем вызове.

Тексты самих смс (в том числе это) можно менять в приложении: Настройки →
Шаблоны СМС.

Для веб-кабинета (`web/`) нужна ещё одна функция — `send-push`: через неё
кабинет шлёт push бригаде (из браузера напрямую в Expo отправить нельзя).

```bash
supabase functions deploy send-push
```

## Что создаётся

7 таблиц одного тенанта (без `org_id` — мультитенантность добавится отдельной
миграцией позже, см. раздел 8 ТЗ): `employees`, `clients`, `services`,
`orders`, `order_stops`, `order_crew`, `order_services`.

Ключевое: `order_crew_check_availability` — триггер на уровне БД, который
не даёт назначить сотрудника на два заказа с пересекающимся временем
(раздел 4, п.8 ТЗ). Это гарантия на стороне базы в дополнение к проверке в
UI при создании заказа (шаг 4).

RLS включён на всех таблицах; `anon key` ничего не читает и не пишет. С
миграции 0005 доступ `authenticated`-пользователей не «всё подряд», а по
роли и правам из `employees` (`is_admin()`/`has_order_permission()`):
создавать/редактировать/удалять заказы и менять роли сотрудников может
только тот, у кого на это есть право (для админа — всегда). Видимость
телефонов клиентов и сумм заказов (`can_view_contacts_and_amounts`)
проверяется только в интерфейсе приложения, не на уровне RLS/колонок —
осознанный компромисс ради скорости, не «дыра», но и не изоляция на
уровне базы.

С миграции 0006 водитель без права `can_manage_orders` тоже может
обновлять заказ (RLS это разрешает через `is_driver()`), но только три
колонки — `scheduled_start`, `scheduled_end`, `actual_price`: остальные
проверяет триггер `orders_restrict_driver_update` (`BEFORE UPDATE`,
сравнивает `OLD`/`NEW` и откатывает попытку с понятной ошибкой). Колонка
`orders.created_by` (тоже 0006) — кто создал заказ, для статистики
администратора по сотрудникам: `order_crew` связывает с заказом только
водителя/грузчика, а `created_by` — диспетчера/админа, который его завёл
(`create_order` проставляет её автоматически).

`create_order(...)` (миграция 0002) — RPC-функция, которой пользуется экран
создания заказа: вставляет заказ + точки маршрута + экипаж одним вызовом.
Если триггер найдёт пересечение по времени у кого-то из экипажа, вся функция
целиком откатывается — не остаётся заказа без назначенного экипажа.

`delete_order(p_order_id)` (миграция 0005) — настоящее удаление заказа
(раньше был только перевод в статус «отменён»); доступно только тем, у кого
есть право `can_manage_orders`.

## Автопарк и рабочий график (миграция 0007)

`vehicles` — машины компании: название, гос номер (обязательны), остальное
опционально (грузоподъёмность, размеры кузова, европаллеты, три
чек-поинта). Заводить и менять может тот же, у кого есть
`can_manage_orders` (как и заказы) — отдельного права под автопарк нет. У
водителя есть машина по умолчанию (`employees.default_vehicle_id`),
диспетчер может назначить другую на конкретный заказ (`orders.vehicle_id`);
машина закрепляется один раз при создании заказа, интерфейса «переназначить
машину после создания» нет.

`employee_days_off` — выходные дни сотрудника: по умолчанию все дни
рабочие, выходной — явная строка на дату. Их правит тот же, у кого есть
`can_manage_orders`, а также сам сотрудник — если у него включено
`employees.can_manage_own_schedule` (галочка в «Команде», выключена по
умолчанию; нужна в первую очередь подрабатывающим грузчикам, которые сами
решают, когда готовы брать заказы). Выходной — это ограничение только для
интерфейса (подсказка диспетчеру), в базе на назначение экипажа он не
влияет: заказ на выходной день создать технически можно.

«Сборный груз»: раньше триггер `order_crew_check_availability` не позволял
назначить сотрудника на два заказа с пересекающимся временем ни в каком
случае. С 0007 это разрешено, только если **обе** пересекающиеся записи —
роль `driver` (один водитель на одной машине одновременно везёт несколько
грузов рейсом). Если хоть одна сторона — `loader`, пересечение по-прежнему
запрещено: грузчик физически не может быть на двух заказах сразу.

Отсюда же — у `order_crew` изменился первичный ключ: было
`(order_id, employee_id)`, стало `(order_id, employee_id, role)`. Это
позволяет водителю дополнительно числиться грузчиком на своём же заказе
(«совмещает функции» — типичный случай: водитель и есть единственный
грузчик в бригаде) — тогда у него две строки на один `order_id` с разной
`role`. Экран заказа сводит их в одну строку интерфейса («Водитель и
грузчик»), а «принять заказ»/статус обновляет обе строки одним действием
(фильтр по `order_id`+`employee_id`, без `role`).

## Режим графика, часы и перенос заказов (миграция 0008)

`employees.schedule_mode` — как сотрудник ведёт свой график: `mark_off`
(отмечает выходные, остальные дни рабочие — так было раньше, это
по-прежнему значение по умолчанию для всех) или `mark_on` (отмечает
рабочие дни, остальные недоступен — удобнее подрабатывающим: «в какие дни
я готов брать заказы», а не наоборот). Меняет только сам сотрудник на
«Моём графике» — это разрешает уже существующая политика `employees
update` (`auth_user_id = auth.uid()`, миграция 0005), новых прав не
понадобилось.

`employee_days_off` переименована в `employee_schedule_days` и получила
явный статус: раньше факт строки всегда значил «выходной», теперь у
строки есть `status` (`'off'`/`'on'`), поэтому смена режима задним числом
не меняет смысл уже проставленных дней. Опциональные `start_time`/
`end_time` сужают рабочий статус до окна в течение дня — заполняются на
«рабочих» днях, у выходного дня часов не бывает (проверяется constraint'ом
`employee_schedule_days_hours_need_on`). Часы — это тоже только подсказка
в форме заказа (сравнение с временем заказа на клиенте), в базе на
назначение экипажа они не влияют, как и раньше с выходными.

Перенос и копирование заказов — это интерфейс поверх уже существующих
прав, без новой миграции: кнопка «Изменить время и сумму» на карточке
заказа (раньше — только у бригады) теперь открыта и диспетчеру/админу,
даже когда сам не в бригаде заказа (RLS это уже разрешала, «orders
update», миграция 0006, просто в интерфейсе не было кнопки); «Копировать
заказ» открывает форму нового заказа, предзаполненную данными исходного.

## Профиль сотрудника (миграция 0009)

`employees` получила четыре новых поля: `last_name`, `birth_date`,
`hire_date`, `address` — все необязательные (`null`, пока не заполнены).
Возраст нигде не хранится — экран «Команда» считает его на лету из
`birth_date`. Заполняются и редактируются в той же карточке сотрудника, что
и логин/пароль/права; читать и менять их может тот же, у кого есть право
`can_manage_orders` (как и остальные поля `employees`), отдельного права
под профиль не заводили.

## Раздел «Настройки» (миграция 0011)

Вход — по имени/роли/аватару в шапке любого экрана (кнопка открывает меню
с пунктами «Настройки» и «Выйти»), доступен всем ролям. Внутри:

- **Мой профиль** — свой логин, телефон, пароль (через ту же функцию
  `update-account`, что и в «Команде», просто теперь она разрешает
  сотруднику менять и свою собственную запись) и «Оплата профиля» —
  показывает уже существующее `employees.paid_until`, «Продлить» пока
  заглушка (кнопка есть, ничего не делает — так и просил Максим).
- **Услуги**, **Шаблоны СМС**, **Напоминания сотрудникам** — только
  администратор (`is_admin()`); `services` до этой миграции разрешала
  запись любому вошедшему (миграция 0001), теперь — только админу.

`sms_templates` — тексты смс клиентам, `[Name]/[Day]/[Date]/[Time]/[Cost]/
[Address]` подставляются автоматически при отправке. Пока по-настоящему
отправляется только `new_order` (при создании заказа, best-effort с
клиента, как и push-уведомления) — остальные три шаблона уже можно
готовить заранее, отправка по ним появится отдельно.

`reminder_rules` + `order_reminder_log` — «за сколько минут напомнить
сотруднику о заказе» (несколько правил, редактируются в Настройках) и
журнал уже отправленных напоминаний (не даёт напомнить дважды по одному
правилу). Отправляет `send-crew-reminders` — её раз в 5 минут вызывает
pg_cron (не приложение), см. деплой выше.

## Если создание заказа падает с ошибкой

Самая частая причина — не выполнена `migrations/0002_create_order_function.sql`
(RPC `create_order`, которой пользуется форма создания заказа). Если в SQL
Editor не выполняли этот файл — выполните, затем повторите попытку в
приложении.

## Вход администратора, диспетчера, водителя, грузчика

С миграции 0005 роль каждого входа — это `employees.role`
(`admin`/`dispatcher`/`driver`/`loader`), а не неявное угадывание. Админ и
диспетчер видят календарь/клиентов (плюс «Команда» — только админ),
водитель и грузчик — список своих заказов на сегодня. Права
`can_manage_orders`/`can_view_client_stats`/`can_view_contacts_and_amounts`
(у админа всегда все три включены) заданы на самой строке `employees`; что
именно каждая роль видит и правит по умолчанию, и что эти три переключателя
меняют поверх роли — см. «Роли и права доступа» в `../mobile/README.md`.

**Обычный способ завести нового диспетчера/водителя/грузчика** — экран
«Команда» в приложении (доступен администратору): там задаётся логин,
пароль и права, ничего в Supabase Dashboard делать не нужно. Вход по
логину работает так: в поле «Логин» можно ввести и обычный email (тогда
он используется как есть — так входит администратор из шага выше), и
короткий логин без email (тогда приложение само превращает его во
внутренний адрес `<логин>@mdtrans.internal` — см. `mobile/src/lib/accountLogin.ts`).

**Вручную через SQL Editor** (для отладки, или если Edge Function ещё не
задеплоена) — тот же приём, что и в разделе «Сделать себя
администратором» выше: создайте пользователя в Authentication → Users,
скопируйте его `UID`, затем
```sql
insert into employees (auth_user_id, name, role, can_manage_orders, can_view_client_stats, can_view_contacts_and_amounts, account_status)
values ('<UID>', 'Имя сотрудника', 'driver', true, true, true, 'active'); -- role: admin/dispatcher/driver/loader
```
