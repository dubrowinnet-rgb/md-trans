# Supabase

## Применить схему

Эта сессия не имеет сетевого доступа к `*.supabase.co`, поэтому миграции нужно
накатить самостоятельно одним из способов:

**Вариант А — SQL Editor в Dashboard (быстрее всего):**
1. Откройте ваш проект → SQL Editor → New query.
2. Скопируйте содержимое `migrations/0001_init_schema.sql` целиком и выполните (Run).
3. Так же выполните `migrations/0002_create_order_function.sql` (нужна для экрана создания заказа)
   и `migrations/0003_push_tokens.sql` (колонка для push-токена сотрудника).
4. Выполните `migrations/0004_services_catalog.sql`: цвета услуг, стартовый
   каталог услуг и новая версия `create_order` (с услугами и обязательным клиентом).
   Без неё новая форма заказа не сохранит заказ.
5. Выполните `migrations/0005_roles_and_permissions.sql`: роли входа
   (администратор/диспетчер/водитель/грузчик), логин и права доступа у
   каждого сотрудника, удаление заказа. **После неё сразу же, до того как
   зайти в приложение заново, выполните шаг «Сделать себя администратором»
   ниже** — иначе ваш текущий вход останется без роли и приложение покажет
   экран «нет доступа».
6. Выполните `migrations/0006_fixed_role_permissions.sql`: узкое право
   водителя редактировать только время и сумму заказа (остальные поля
   заблокированы триггером в базе, а не только в интерфейсе) и колонка
   `orders.created_by` для статистики администратора по сотрудникам.

**Вариант Б — Supabase CLI (если он у вас установлен локально):**
```bash
supabase link --project-ref mjrbqnsvwohmwvapiikr
supabase db push
```

## ⚠️ Сделать себя администратором (обязательно после миграции 0005)

До миграции 0005 роль определялась неявно: вход без строки в `employees`
считался диспетчером с полным доступом — так работал и ваш текущий вход.
После миграции 0005 это правило убрано (иначе любой новый вход был бы
диспетчером по умолчанию — дыра в безопасности), и вход без строки в
`employees` видит экран «нет доступа». Чтобы не потерять доступ к
собственному приложению, сразу после 0005 выполните в SQL Editor:

1. Authentication → Users → найдите свою запись (по email, которым входите
   в приложение) → скопируйте её `UID`.
2. Выполните, подставив свой UID:
   ```sql
   insert into employees (auth_user_id, name, role, can_manage_orders, can_view_client_stats, can_view_contacts_and_amounts, account_status)
   values ('<ваш UID из шага 1>', 'Максим', 'admin', true, true, true, 'active')
   on conflict (auth_user_id) do update set
     role = 'admin',
     can_manage_orders = true,
     can_view_client_stats = true,
     can_view_contacts_and_amounts = true;
   ```
3. Перезайдите в приложение (или потяните экран, чтобы обновить сессию) —
   должна появиться вкладка «Команда». Дальше диспетчеров, водителей и
   грузчиков можно заводить прямо в приложении, без SQL.

## Деплой Edge Function (нужна для создания аккаунтов из приложения)

Экран «Команда» заводит логин и пароль сотруднику через серверную функцию
`create-account` — с телефона нельзя напрямую задать пароль пользователю
(для этого нужен service role key, а он не должен попадать в приложение).
Без деплоя эта функция недоступна, и кнопка «Добавить» на экране «Команда»
будет возвращать ошибку.

```bash
supabase link --project-ref mjrbqnsvwohmwvapiikr   # если ещё не делали
supabase functions deploy create-account
```

Больше ничего настраивать не нужно: `SUPABASE_URL`, `SUPABASE_ANON_KEY` и
`SUPABASE_SERVICE_ROLE_KEY` функция получает от платформы автоматически.

## Что создаётся

7 таблиц одного тенанта (без `org_id` — мультитенантность добавится отдельной
миграцией позже, см. раздел 8 ТЗ): `employees`, `clients`, `services`,
`orders`, `order_stops`, `order_crew`, `order_services`.

Ключевое: `order_crew_check_availability` — триггер на уровне БД, который
не даёт назначить сотрудника на два заказа с пересекающимся временем
(раздел 4, п.8 ТЗ). Это гарантия на стороне базы в дополнение к проверке в
UI при создании заказа (шаг 4).

RLS включён на всех таблицах; `anon key` ничего не читает и не пишет. С
миграции 0005 доступ `authenticated`-пользователей не «всё подряд», а по
роли и правам из `employees` (`is_admin()`/`has_order_permission()`):
создавать/редактировать/удалять заказы и менять роли сотрудников может
только тот, у кого на это есть право (для админа — всегда). Видимость
телефонов клиентов и сумм заказов (`can_view_contacts_and_amounts`)
проверяется только в интерфейсе приложения, не на уровне RLS/колонок —
осознанный компромисс ради скорости, не «дыра», но и не изоляция на
уровне базы.

С миграции 0006 водитель без права `can_manage_orders` тоже может
обновлять заказ (RLS это разрешает через `is_driver()`), но только три
колонки — `scheduled_start`, `scheduled_end`, `actual_price`: остальные
проверяет триггер `orders_restrict_driver_update` (`BEFORE UPDATE`,
сравнивает `OLD`/`NEW` и откатывает попытку с понятной ошибкой). Колонка
`orders.created_by` (тоже 0006) — кто создал заказ, для статистики
администратора по сотрудникам: `order_crew` связывает с заказом только
водителя/грузчика, а `created_by` — диспетчера/админа, который его завёл
(`create_order` проставляет её автоматически).

`create_order(...)` (миграция 0002) — RPC-функция, которой пользуется экран
создания заказа: вставляет заказ + точки маршрута + экипаж одним вызовом.
Если триггер найдёт пересечение по времени у кого-то из экипажа, вся функция
целиком откатывается — не остаётся заказа без назначенного экипажа.

`delete_order(p_order_id)` (миграция 0005) — настоящее удаление заказа
(раньше был только перевод в статус «отменён»); доступно только тем, у кого
есть право `can_manage_orders`.

## Тестовые данные

Экран календаря показывает «Нет ни одного сотрудника», пока в `employees`
пусто. `seed_example.sql` — набор из 2 водителей, 2 грузчиков и пары

заводить сотрудников вручную.

## Если создание заказа падает с ошибкой

Самая частая причина — не выполнена `migrations/0002_create_order_function.sql`
(RPC `create_order`, которой пользуется форма создания заказа). Если в SQL
Editor не выполняли этот файл — выполните, затем повторите попытку в
приложении.

## Вход администратора, диспетчера, водителя, грузчика

С миграции 0005 роль каждого входа — это `employees.role`
(`admin`/`dispatcher`/`driver`/`loader`), а не неявное угадывание. Админ и
диспетчер видят календарь/клиентов (плюс «Команда» — только админ),
водитель и грузчик — список своих заказов на сегодня. Права
`can_manage_orders`/`can_view_client_stats`/`can_view_contacts_and_amounts`
(у админа всегда все три включены) заданы на самой строке `employees`; что
именно каждая роль видит и правит по умолчанию, и что эти три переключателя
меняют поверх роли — см. «Роли и права доступа» в `../mobile/README.md`.

**Обычный способ завести нового диспетчера/водителя/грузчика** — экран
«Команда» в приложении (доступен администратору): там задаётся логин,
пароль и права, ничего в Supabase Dashboard делать не нужно. Вход по
логину работает так: в поле «Логин» можно ввести и обычный email (тогда
он используется как есть — так входит администратор из шага выше), и
короткий логин без email (тогда приложение само превращает его во
внутренний адрес `<логин>@mdtrans.internal` — см. `mobile/src/lib/accountLogin.ts`).

**Вручную через SQL Editor** (для отладки, или если Edge Function ещё не
задеплоена) — тот же приём, что и в разделе «Сделать себя
администратором» выше: создайте пользователя в Authentication → Users,
скопируйте его `UID`, затем
```sql
insert into employees (auth_user_id, name, role, can_manage_orders, can_view_client_stats, can_view_contacts_and_amounts, account_status)
values ('<UID>', 'Имя сотрудника', 'driver', true, true, true, 'active'); -- role: admin/dispatcher/driver/loader
```
